# Proposed v0.1.0-pre-alpha.2 Release Notes

**Status:** Proposed; not tagged and not published.

This governance prerelease activates the structured public risk-event store,
publishes an evidence-adjudicated historical batch through 2026-09-22, and
adds repeatable validation and review. Hydra Core remains pre-v1, and the
public-user posture remains invite-only preparation with read-only forward
shadow planned and public-user execution disabled.

## Governance Changes

- publishes selected V1 records under `risk-events/YYYY/`, indexed by their
  evidence-supported UTC occurrence time rather than their publication date
- validates schemas, event identities, occurrence-year partitions, chronology,
  relationships, and public evidence references as one collection
- records the shadow-advisory authority escape and maintenance-transport
  interruption as distinct failure and recovery contracts
- requires interval-wide history, terminal-intent, preserved risk-anchor,
  identity, and fresh-source evidence for interruption recovery
- renews the dated public-user posture and adds a weekly read-only staleness
  check that fails after its declared boundary
- adds material-change and monthly ledger-review guidance plus a sanitized
  public coordination template

## Migration Notes

Published V1 events now live at `risk-events/YYYY/<event_id>.json`. Consumers
must treat `occurred_at` as the historical event or transition time and
`recorded_at` as the later public preparation time. Filename identity and the
UTC occurrence-year partition are enforced.

`correction_of` and `supersedes` may point only to an earlier published event.
Local public evidence references must resolve inside this repository; external
references must use HTTP or HTTPS. Existing structured records are immutable,
and corrections append a linked record.

Automated consumers should run the deterministic validator for ordinary
changes and `--check freshness --as-of now` for current posture presentation.
The weekly workflow performs that current-time check with read-only repository
permissions.

Recovery implementations must keep broker-disconnect and maintenance-transport
classification separate. Shadow or advisory outputs may be recorded, but they
cannot replace or resize the authoritative candidate passed to a live gate.

## Evidence And Claim Boundary

The published batch is selected public governance history, not a complete
incident register, trading journal, performance record, or current private
permission. Deferred events lacked an exact supported transition time or
separate authoritative rearm evidence. Terminal rejections do not establish a
missed fill, hypothetical profit and loss, or broker execution.

No private implementation, protected parameters, account material, or
real-time execution state was published. No public-user broker connection,
order submission, or live execution was enabled.

## Validation

The candidate tree passed:

- Python unit tests covering event storage, collection semantics, public
  boundaries, recovery contracts, posture freshness, and workflow policy
- deterministic public-surface validation, including JSON Schema Draft 2020-12
- current-time public-posture freshness validation
- locked Node dependency installation and Markdown lint
- repository diff and public-boundary checks

External links are checked separately with bounded retries and timeouts.
